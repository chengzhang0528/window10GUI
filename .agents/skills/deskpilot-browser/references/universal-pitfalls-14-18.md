# 通用坑与处理办法（续：#14–#18）

> 接前篇 `universal-pitfalls.md`；本册覆盖坑 #14–#18，续篇 `universal-pitfalls-19-21.md`。

## 14. 浮层遮挡：点击"命中了自己"却到不了目标

**现象**：弹窗底部的「取消」按钮明明在视口内、`elementFromPoint` 返回它自己、`pointer-events:auto`，但 `chrome.click` 点下去弹窗就是关不掉，`残留弹窗=1` 一路污染后续所有字段。

**根因**：一个**冻结的自动填充（autocomplete）浮层**盖在按钮上方，把真实点击吃掉了。`elementFromPoint` 看的是 DOM 命中测试，而**浏览器原生 UI 浮层不属于页面 DOM**，所以页面内任何探测都看不见它 —— 只有 UIA 树能看到（实测是 `PopupViewViews`「自动填充」）。

**解法**：关弹窗前**先按一次 Esc** 收掉原生浮层，再点按钮；并把"回读可见弹窗数"作为唯一成功判据：

```
for attempt in 1..3:
    if 可见弹窗数 == 0: 成功
    press Esc            # 收掉原生浮层
    if 可见弹窗数 == 0: 成功
    点「取消」(先 scrollIntoView)  /  点 X  /  Esc
回读可见弹窗数作为结果
```

**验证**：加 Esc 后同一按钮一次点掉（`modalsLeft: 0`）。

**教训**：页面内 DOM 探测有盲区 —— **浏览器自身的 UI（自动填充、翻译条、权限气泡）不在 DOM 里**。当"DOM 说可点、点了却无效"时，用 UIA/截图看，而不是继续加 DOM 断言。

## 15. 等待要等"状态出现"，不要 sleep 固定秒数

**现象**：每个弹窗字段点开后 `sleep 2000` 再读。实测弹窗**慢一帧**出现时，本字段读到"无弹窗"（`open=0`），而它的弹窗会在**下一个字段**才渲染 —— 表现为"弹窗慢一个字段"：项目号打开时 count=0、经费打开时却读到 `SAP_项目号`。逐字段错位又回来了。

**解法**：轮询等待**目标状态**出现，而不是固定延时：

```
for i in 1..16:
    titles = 当前可见弹窗标题
    if expect_title and expect_title in titles: break
    if not expect_title and titles: break
    sleep 300ms
```

**教训**：固定 sleep 的两种失败方式都遇到过 —— 太短则读到旧状态，太长则白等。**以"期望状态是否出现"为循环条件**才既稳又快。

**加强版（2026-09-23 实测踩到）**：条件要精确到"**你真正要的那个东西**"，不能是"有东西了"。搜完等结果时用「行数 > 0」作条件会**过早通过** —— 搜索请求还没回来时弹窗显示的仍是首页旧数据（10 行），于是循环立刻判定"已完成"，紧接着在旧数据里找目标，报 `row_not_found(rows=10)`。

```
✗ 轮询 "行数 > 0"          → 旧数据满足条件，过早退出
✓ 轮询 "目标行是否已出现"    → 只有新结果到了才退出
```

改后同一场景有值字段从 15 提升到 18，连跑 3 次结果一致。**写等待条件时问一句：这个条件在"旧状态"下会不会也成立？会，就写错了。**

## 16. 表格选行：先整格精确，再前缀，最后才子串

**现象**：按"行文本包含目标值"选行，pick=`0` 时命中了「无项目 | 0 | 1001」这一行，把项目号填成了 `0`。步骤报"选到了行"，实际**选错了行**。

**根因**：纯子串匹配在目标值**短**、或与其它单元格有**包含关系**时必然出错（`"0"` ⊂ `"1001"`、`"1201"` ⊂ `"12010"`）。而"选到行"和"选对行"是两件事。

**解法**：三级匹配，从最严到最松：

```
1) 单元格 === 目标        ← 整格相等，首选
2) 单元格 startsWith 目标  ← 容忍 "1206-CO" 这类后缀写法
3) 行文本 includes 目标    ← 最后兜底，并应视为"弱匹配"
```

**验证**：用同一弹窗对同一目标值跑两级，确认第 1 级命中；对短值（如 `0`）必须验证不会误中。

**教训**：匹配规则要按**严格度降级**写，不要一上来就用最松的。越松的匹配越要在日志里标明是弱匹配，否则"歪打正着"会被当成成功。

## 17. 内联脚本里的 `\s` 会被模板字面量吃掉 —— 正则静默变成裸字母

**现象**：一个多行内联脚本（模板字面量）里的正则 `/\\s+/g`、`/共\\s*(\\d+)\\s*条/`，运行到浏览器时变成了 `/s+/g`、`/共s*(d+)s*条/` —— **反斜杠整个消失**，`\d` 变 `d`，`\)` 之类还会让整段脚本报 `SyntaxError: Unexpected token ')'`。

**根因**：模板字面量里 `\s` 是**转义序列**，JS 会把它解析成 `s`。要让它到浏览器时仍是 `\s`，源码里必须写 `\\s`（双反斜杠）。写单反斜杠时**不报错**，只是静默变成裸字母 —— 正则仍然"能跑"，但语义全错（匹配字面量 `s` 而不是空白符）。

**为什么极难发现**：
1. 文件本身 `node --check` 通过（语法合法）；
2. 单反斜杠时脚本能跑，只是结果错（比如分页解析全为 null），**不抛错**；
3. 一旦某个 `\(` `\)` `\/` 被吃掉，才变成 `SyntaxError`，而错误信息只有一句 `Unexpected token ')'`，完全指不到位置；
4. 用"手工切字符串"的调试脚本验证会**掩盖**它 —— 手工切不经过 JS 转义。必须用 `vm.runInContext` 执行源码文本，或直接看运行时的字符串。

**解法与自检**：
- 内联脚本里凡是要传给正则/字符串转义的反斜杠，**一律写 `\\`**。
- 写完后用运行时的字符串自检，而不是源码文本：

```js
const ctx = vm.createContext({});
const expr = vm.runInContext(`${declSrc}\n; EXPR_NAME`, ctx);  // 让引擎处理转义
new Function(expr);                                            // 语法检查
// 再打印关键行，肉眼确认是 /\\s+/ 而不是 /s+/
```

**验证**：修好后运行时长从 2478 → 2490（差的 12 个字符正是被吃掉的反斜杠），`SyntaxError` 消失，表达式正常返回。

**教训**：**"文件语法通过"不等于"发出去的脚本是对的"**。生成式内联脚本要检查**生成结果**，不是模板源码。

## 18. 明细行：写进"还没被创建出来的那一行" —— w=0 却 verified:true
**现象**：一张带明细表的表单（ERP 物料申请），明细列按 `#fieldNNNNN_0`（`_0` = 第 0 行）逐列填写。引擎对每一列都报 `verified: true`，但整轮回读全是 `(未渲染)` / 空串。手工探测 `#field67789_0` 得到 `INPUT, w=0, h=0, value=""`。

**根因**：明细行的输入框**在 DOM 里本来就存在**（作为隐藏模板行），但**行本身还没被创建**。脚本用页面内 `btn.click()` 点「新增行」按钮（`#addbutton0`），而这是个不可信事件 —— 按钮没响应，行没被创建。于是后续所有写入都落进一个 **0×0 的游离 input**：`chrome.fill` 照样报 `verified: true`，因为它是"往这个元素里写了值"，不是"值进了表单模型"。

**两个互相掩盖的假象**（所以极难定位）：
1. 选择器**是对的**（`[id="field67789_0"]` 精确命中，只有 1 个节点），所以"查选择器"这条常规排查路走不通；
2. 写入**不报错**且 `verified: true`，所以"看返回值"这条常规排查路也走不通。

**解法**：
1. 「新增行」这类**改变 DOM 结构**的按钮，必须用 `chrome.click`（CDP 可信输入），不能用页面内 `.click()` —— 与 #10 同源。
2. 点击后**回读行数**（不是回读按钮状态），确认行真的出现了，再开始写列。
3. 写入前先断言**目标元素的尺寸非零**；`w==0 && h==0` 时报"该行尚未创建"，而不是继续写。

**验证**：新增行前 `#fieldNNNNN_0` 为 `w=0,h=0`；新增行后同一 id 变为 `w>0`，此时写入才可回读到值。

**但 2026-09-23 实测的更狠一层：`id` 本身重复，且 `getElementById` 取到的是"隐藏的那个"。**

实测同一页面上有两个 `id="addbutton0"`（两张明细表各一个），祖先链完全同名（都是 `TD.detail_1_0_0.etype_10`）：

| 节点 | addbutton 尺寸 | 祖先 TD 尺寸 | 说明 |
|---|---|---|---|
| 第 1 个 | `0 × 0` | `0 × 0` | 隐藏的明细表 |
| 第 2 个 | `20 × 20` | `2458 × 30` | 真正渲染出来的明细表 |

于是 `document.getElementById('addbutton0')` **永远返回第 1 个**（0×0），点它毫无反应；`chrome.click` 则报
`CHROME_ELEMENT_NOT_ACTIONABLE`。而"选择器命中""元素存在""id 唯一"这些常规自检**全部通过**，因为 `id` 在 HTML 里重复了，(按 id 查)本来就只能拿到第一个。

**解法**：凡按 `id` 或 `querySelector` 取到的元素，**先过滤尺寸**，取**已渲染**的那个：

```js
const cands = Array.from(document.querySelectorAll('[id="addbutton0"]'));
const btn = cands.find(b => { const r = b.getBoundingClientRect(); return r.width > 0 && r.height > 0; });
```

若一个都没有渲染出来，就报"该明细表当前未显示"，**不要**退回去点第一个 —— 那正是静默无效的来源。

**教训**：`id` 重复 + `getElementById` 取首个 = 一个**看起来完全正常**的选择器指向错误的节点。同类问题还有 `#field67789_0` 这类**跨表复用 id** 的字段（详见 #11 的 fieldname 去重）。判定"哪个节点才算数"的统一标准只有一个：**它真的渲染出来了吗（宽高 > 0）**。
